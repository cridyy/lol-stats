# Agent Note: 将战绩 SQLite 主数据库限制在 1 GiB

Status: implemented

## Problem

`lol-stats.sqlite3` 保存长期战绩和聚合结果，现有的 12 小时快捷查人缓存限制不能约束其他表。持续查询不同玩家会让数据库不断增长。用户要求最大 1 GB，并在 0.8.3 公开源码。

## Decision

- 以 1 GiB（1,073,741,824 bytes）作为 SQLite 主数据库文件的硬上限；每个连接按实际 page_size 设置 max_page_count，防止单次大写入或并发写入越过上限。
- 页面占用接近上限时才维护缓存，优先按 stored_at_ms 淘汰最旧记录，保留较新的数据。触发点为 90%，清理目标为 80%；联动移除被淘汰对局的玩家索引和失去对局的快捷查人元数据。
- 已有数据库超过上限时先清理再 VACUUM，重设页数上限；普通读写不全库扫描或 VACUUM。保留现有 schema_version，避免升级时无差别清空全部缓存。
- 保留 WAL，设置 checkpoint 和 journal_size_limit 控制检查点后的日志占用。主库硬上限不等于含活动 WAL、SHM 和 VACUUM 临时文件的总目录配额，持有读事务时 WAL 仍可能临时增长。
- 缓存维护失败继续沿用缓存可用性边界并记录错误；不更改战绩评分或网络代理，验证仅使用临时数据库。版本清单、文档和本地更新说明统一为 0.8.3，源码沿用现有 GitHub main 发布。

## Alternatives considered

- 只设置 max_page_count：SQLite 自身提供可靠的写入硬上限，改动最小。但写满后会持续丢失新缓存，已有超限文件也不会自动缩小，因此同时加入旧缓存淘汰与超限收缩。
- 每次写入都按文件大小清理并 VACUUM：容易理解，文件体积能及时下降。但会反复重写数据库，尤其不适合实时战绩的频繁读写，因此只在接近容量上限时清理，已有超限文件才做全库收缩。
- 达到上限就删除整个数据库：实现简单，空间释放最彻底。但会同时丢失近期缓存并引发重新请求，因此采用按时间淘汰。

## Testing

- cargo test --manifest-path .\src-tauri\Cargo.toml cache_capacity_ -- --nocapture：6 项通过，覆盖生产 1 GiB 配置、大写入回滚与重新打开、最旧数据淘汰与跨服索引一致性、已有超限文件收缩、空闲页复用及低占用保留。
- 同一临时库输入（1 MiB 上限、96 条记录、每条 16 KiB）运行原始和修改后的生产初始化代码：原始与回滚均为 1,708,032 bytes、96 条；修改后为 954,368 bytes、47 条，保留最新记录 95。三次 integrity_check 均为 ok，退出码均为 0。
- 回滚仅在单独的源码副本执行，其 SHA256 与原始文件一致。统一补丁在 core.autocrlf=false 下重建修改文件，SHA256 一致。小容量探针验证同一算法，生产测试另行确认常量为 1 GiB，没有创建 1 GiB 测试文件或接触真实用户数据库。
- npm run verify：前端构建、评分边界、Rust 编译与测试全部通过（96 通过、13 项依赖真实客户端或外部环境的手动测试忽略）。

## Consequences

主库不能因新的写入超过 1 GiB，旧缓存优先让位于较新的缓存；清理后的空闲页可复用。由于保留最近缓存，升级不会无差别清空数据库。再次查询被淘汰的记录需要重新请求数据。

只有升级前已经超限的数据库进行 VACUUM，它有额外 I/O 与临时磁盘空间需求；并发读写占用可能让本次维护失败，后续连接重试。检查点不会删除活动日志，含活动 WAL、SHM 与临时文件的总目录占用可能超过主库上限。若产品需要整个目录的严格磁盘配额，需要重新评估日志模式或文件系统级配额，不能将 journal_size_limit 当作活动 WAL 的硬限制。
