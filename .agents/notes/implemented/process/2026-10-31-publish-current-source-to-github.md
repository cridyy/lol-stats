# Agent Note: 公开当前版本源码并建立笔记校验入口

Status: implemented

## Problem

GitHub 的 `cridyy/lol-stats` 已是公开仓库，但远端 `main` 停留在早期版本。本地包含后续提交及尚未提交的识别、图标和快捷换英雄改动，当前发布版本为 0.8.3。README 仍显示 0.7.0，更新说明仍声称源码尚未公开，无法准确指导读者构建当前软件。

仓库还没有 `.agents/notes` 和 `npm run verify-notes`，需要把新的维护约束落实为项目内可执行的检查。

## Decision

- 以 `lol-stats` 内层 Git 仓库为唯一发布对象，在现有 `main` 上追加提交并正常推送至已有 GitHub 远端，保留历史和现有 MIT 许可证。
- 发布当前工程的源码、必要的 ncnn 库和 OCR 模型、现有品牌素材。保留外层工作区及其他项目；日志、构建目录、数据库和本地凭据不纳入提交。
- 更新 README 的版本、胜率识别和快捷交换说明，补充 ncnn 与 PaddleOCR 的许可证和来源；更新本地更新清单中的源码公开说明。
- 引入笔记技能提供的目录、格式和归档校验脚本，通过 `tsx` 在 Node.js 20 及以上版本运行；新增统一的 `verify-notes` npm 入口。
- 本次发布源码，保留已有历史，不创建二进制 Release，不推送 Gitee。评分保持现有行为；数据库容量的新约束由关联笔记管理。

## Alternatives considered

- 新建一个仅含当前源码的仓库：发布内容最容易隔离，也不依赖旧仓库状态。但用户明确希望使用已有仓库，这会丢失现有地址、历史和贡献关联，因此不采用。
- 只推送已提交历史：无需触碰工作区，操作最少。但当前的识别与快捷换英雄修复尚未提交，会公开一个落后的版本，因此纳入当前工程改动后再推送。
- 笔记只通过开发者机器上的脚本校验：无需给项目增加开发依赖。但其他贡献者无法在克隆后执行同一个检查命令，因此将检查脚本和运行依赖放进仓库。

## Testing

- npm run verify 完成前端构建、评分边界、Rust 编译与单元测试：96 通过、13 项真实客户端或网络手动测试忽略。
- 必需的模型、原生库和封面文件存在且小于 GitHub 单文件限制；当前变更和待发布历史的敏感信息扫描没有发现真实凭据。
- 发布采用普通 main 分支推送，以远端提交 SHA 与本地 HEAD 一致作为验收事件；发布命令和最终 SHA 另存外部验证记录，避免自引用提交哈希。

## Consequences

GitHub 继续沿用公开的既有地址、MIT 许可证和贡献历史，克隆后可以直接执行笔记校验。第三方数据服务和真实客户端环境影响手动验证，自动检查不证明所有游戏画面都能识别。OCR 模型与原生库增加克隆体积，需要保留对应许可声明；其历史精确构建参数未记录，不宣称二进制构建可复现。
